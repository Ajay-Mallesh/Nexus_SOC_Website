Project Introduction

Multi-Voltage Nexus SoC Architecture

The Nexus SoC is a 32nm system-on-chip with approximately 200K standard cells post-synthesis and a complex 12-clock architecture. The design uses three voltage domains to balance high-speed data throughput and power efficiency.

Voltage Domains

  • High-Performance Domain (1.05V / VDDH): Latency-critical, high-bandwidth TX/RX data links.
  • Default Domain (0.85V / VDD): Core processing, SDRAM interfaces, and system monitoring.
  • Low-Power Domain (0.78V / VDDL): Background tasks and low-speed serial peripherals.

Physical Design Challenges

  • UPF power intent integration and safe cascaded level-shifter crossings between all three domains.
  • CTS for 11 physical clocks and one virtual clock using an H-Tree topology and NDR.
  • Dedicated voltage areas and an M7/M8 triple-domain power mesh.
  • MCMM closure, 200MHz-to-400MHz multi-cycle paths, and signoff at FF -40°C / SS 125°C.

UPF - Multi-Voltage Power Intent Design

Developed a Unified Power Format (UPF) specification for the Nexus SoC, enabling power-aware implementation and verification across the 1.05V high-performance, 0.85V default, and 0.78V low-power domains.

Power Intent Architecture

The UPF defines power domains, supply ports and nets, domain-specific power connections, operating states, and a comprehensive Power State Table (PST). Explicit voltage-threshold tolerances permit direct 0.85V-to-0.78V crossings; larger voltage differences involving the 1.05V domain use isolation, translation, and cascaded bridges.

How We Achieved a Power Domain Without a Level Shifter

The 0.78V low-power domain connects directly to the 0.85V default domain without level shifters. The direct crossing uses the 70mV voltage difference, 32nm standard-cell library noise margins, and threshold-voltage (Vth) tolerances configured in UPF.

  • Small voltage delta: The 0.85V ↔ 0.78V crossing differs by only 70mV.
  • Library-aware tolerance: UPF voltage thresholds account for the library's noise margins and Vth tolerances.
  • No level shifter on this crossing: Direct connection avoids extra cell area, timing-path insertion delay, and leakage.
  • Larger voltage differences: Crossings involving the 1.05V domain use strict isolation and translation with vddh_cascade_buffer.v and UPF-configured level shifters.
  • Intermediate staging: For a 0.78V-to-0.85V transfer through the high-performance domain, vddh_cascade_buffer.v stages the signal at 1.05V before it is translated down to 0.85V.

This distinction keeps the near-voltage domains efficient while protecting transfers that span the larger voltage difference.

Key Features

  • Defined separate power domains (PD_HIGH at 1.05V, DEFAULT_VA at 0.85V, and PD_LP at 0.78V) for distinct functional blocks.
  • Created supply ports, supply nets, and primary power/ground connections for a triple-supply architecture.
  • Configured precise voltage operating states and a Power State Table for all three domains.
  • Developed comprehensive Power State Tables (PST) to accurately represent valid, complex system power modes.
  • Used level-shifterless crossings between 0.85V and 0.78V by exploiting configured voltage tolerances and library noise margins.
  • Managed larger, unsafe crossings involving 1.05V using vddh_cascade_buffer.v alongside automated level shifters; the buffer stages signals at 1.05V before translation to 0.85V.
  • Enabled power-aware simulation, multi-voltage synthesis, place-and-route, and signoff flows.
  • Designed according to industry-standard low-power ASIC methodologies.
  • Supported seamless integration between RTL, UPF, and physical design implementation.

  • Primary engine: Clocks the 384-stage × 512-bit u_core_unit pipeline and 32 SRAMLP2RW128x16 macros in u_risc_reg at 0.85V.
  • Multi-voltage CTS span: Also clocks u_cascade_bridge in PD_HIGH and the final master_sig_out register in DEFAULT_VA; balance these endpoints across the domain crossing.

2. High-Performance 1.05V PCI Clocks (clk_h_tx, clk_h_rx)

  • clk_h_tx clocks the read side of fifo_pci and the 50 TX SRAMs across u_pci_tx_0 / u_pci_tx_1.
  • clk_h_rx independently clocks the 50 RX SRAMs across u_pci_rx_0 / u_pci_rx_1; both high-speed clocks use a 0.10ns max-transition target on M4–M6 NDR routes.

3. SDRAM Memory Subsystem Clocks (clk_sdram_0–clk_sdram_3)

  • clk_sdram_0 clocks the fifo_sdram read side and 36 SRAMLP2RW32x4 macros in u_sdram_ctrl.
  • clk_sdram_1, clk_sdram_2, and clk_sdram_3 are top-level roots reserved for quad-channel SDRAM banking and multi-root CTS balancing.

4. Fault-Tolerant Multi-Cycle Clocks (clk_ft_0, clk_ft_1)

These 200MHz half-rate roots are checked against the 400MHz master domain using set_multicycle_path 2 -setup and set_multicycle_path 1 -hold during MCMM optimization and PrimeTime DMSA signoff.

5. Ultra-Low-Power 0.78V Clocks (clk_lp_tx, clk_lp_rx)

Each root stays inside PD_LP and drives a 64-stage × 128-bit lp_logic_pipe and 16 SRAMLP2RW64x8 context RAMs. Data crosses toward the cascade bridge under the configured 70mV level-shifterless voltage tolerance.

6. Virtual I/O Boundary Clock (vclk_io)

Defined only in SDC, with no physical port in nexus_soc_top.v, this virtual clock provides launch/capture references for sys_data_in[31:0] and master_sig_out[127:0]. It constrains PrimeTime I/O timing without creating physical CTS buffers.

Setup and Hold Fixes

Achieving timing closure for the Nexus SoC requires rigorous setup and hold optimization across multiple PVT corners in the MCMM environment.

⚠️ Note: Both insert_buffer and upsize_cell manual scripts are not recommended in the standard ICC2 flow. For production silicon, always rely on native route_opt or PrimeTime DMSA ECO generation to resolve timing violations, as they account for accurate 3D SPEF parasitics and complex routing design rules.

Available Fixes for Setup Violations

Setup violations occur when the data path is too slow. The following optimization techniques are available to speed up the data arrival time:

  • Cell Upsizing: Replacing a driver with a higher drive-strength standard cell to push the capacitive load faster.
  • Buffer Insertion: Breaking long, highly capacitive nets by inserting high-drive buffers to improve signal transition.
  • VT Swapping (LVT): Swapping High-VT or Regular-VT cells with Low-VT (LVT) variants for faster switching speed (at the cost of higher leakage power).
  • Path Restructuring: Cloning logic or pulling standard cells closer together during placement to reduce wire delay.
  • Automated Flow: Using route_opt in ICC2 or executing a targeted fix_eco_timing -setup script exported from PrimeTime.
View Upsize Cell Script on GitHub View Insert Buffer Script on GitHub

Available Fixes for Hold Violations

Hold violations occur when the data path is too fast, causing data to be prematurely overwritten at the capturing flip-flop. The following techniques are used to slow down the data path:

  • Delay Buffer Insertion: Adding specialized delay cells or buffers (e.g., DELLN*_HVT) directly into the fast data path to intentionally increase delay without affecting logic.
  • Cell Downsizing: Reducing the drive strength of a cell to intentionally slow down its transition and delay time.
  • VT Swapping (HVT): Swapping LVT/RVT cells for High-VT (HVT) cells to slow down the path, which also provides the benefit of saving leakage power.
  • Automated Flow: Using route_opt -hold in ICC2 or executing a targeted fix_eco_timing -hold script exported from PrimeTime (usually performed only after CTS and detailed routing).

Macro and Port Location Extraction Script

This Tcl-based utility extracts the physical X/Y locations of hard macros and I/O ports into simple text files, making floorplan reuse, ECO migration, and layout backup much faster and more reliable.

  • Captures port locations from bbox data into a reusable file
  • Captures hard macro origin points from origin data for placement restoration
  • Useful for floorplan preservation, hierarchical top-down design, and cross-tool workflow portability

In physical design, this is valuable because a floorplan can be lost during a tool crash, netlist update, or fresh implementation run. With the extracted coordinates, you can restore the layout in minutes instead of redoing manual placement.

Advantages
  • Floorplan preservation: protects your macro and port placement from being lost during crashes or re-runs
  • ECO-friendly: helps carry forward placement when netlists are updated
  • Hierarchical reuse: enables top-down design teams to share the same placement blueprint
  • Cross-tool compatibility: stores data in a simple text format that can be reused across EDA flows
Flexibility and Extensions
  • Filter only specific macros such as SRAMs or RAM-based blocks
  • Capture orientation data if rotated or flipped macros are important
  • Generate direct placement commands instead of plain coordinates
  • Adapt the output format for custom Python, Perl, or Tcl-based automation
Example Tcl Flow
# Extract Ports to a clean file
set p_fp [open "./docs/port_locations.tcl" "w"]
foreach_in_collection port [get_ports] {
    set box [get_attribute $port bbox]
    if {$box != ""} {
        set loc [lindex $box 0]
        puts $p_fp "[get_object_name $port] $loc"
    }
}
close $p_fp

# Extract Macros to a clean file
set m_fp [open "./docs/macro_locations.tcl" "w"]
foreach_in_collection cell [get_cells -hierarchical -filter "is_hard_macro"] {
    set loc [get_attribute $cell origin]
    if {$loc != ""} {
        puts $m_fp "[get_object_name $cell] $loc"
    }
}
close $m_fp
